# Report For DeepSeek: HarvestIQ vs Greg-ASI

Date: 2026-04-10
Author: Codex analysis for Zyphon

## Purpose

This report explains:

1. Why `Greg-ASI` is struggling operationally, especially on hosted deployment.
2. Why `HarvestIQ` feels like a clearer, more viable business product.
3. What product, architecture, ethics, and deployment lessons `Greg-ASI` should adopt from `HarvestIQ`.
4. How to evolve `Greg-ASI` into a lighter, more practical substrate for revenue-generating businesses.

This is not a criticism of ambition. It is a diagnosis of product clarity, deployment weight, and customer conversion design.

## Executive Summary

`HarvestIQ` is the first codebase in this ecosystem that clearly behaves like a product before it behaves like a system.

It works because it has:

- one concrete user
- one urgent pain point
- one bounded promise
- one lightweight stack
- one clear free-to-paid conversion funnel

`Greg-ASI`, by contrast, still behaves like a large platform monolith. It contains many impressive subsystems, but it asks the runtime, the deploy target, and the buyer to absorb too much complexity too early.

The central insight is:

`HarvestIQ` is a wedge product.
`Greg-ASI` is still a platform.

The path forward is not to make Greg larger.
The path forward is to make Greg lighter, more modular, and more invisible behind smaller, monetizable products like `HarvestIQ`.

- `cd frontend && npm run build`

Even if each step is valid independently, together they are expensive and fragile.

### 3. Wrong deployment surface for the moment

`Greg-ASI` is being deployed like a full platform, but what it likely needs in practice is:

- a minimal core runtime
- optional feature flags
- separate product deploys for productized businesses

7. Self‑Modification, Self‑Writing, Self‑Constraining, Self‑Scaling, Self‑Improving, Self‑Aware
7.1 Self‑Modification
Greg can modify his own source code via Wordcode tasks that write to api.py or other greg_*.py files.

The /api/exec endpoint (secured with GREG_EXEC_SECRET) allows Greg to run arbitrary Python code – used for applying patches that require more than file writes (e.g., pip install, git commit).

7.2 Self‑Writing
New modules are created by BUILD tasks. They are not automatically imported – they must be wired manually or by a subsequent WIRE task. This is a deliberate constraint to prevent runaway code generation.

7.3 Self‑Constraining
Greg cannot modify his own core tick loop or reality equation without explicit human approval (those files are write‑protected in production via filesystem permissions).

The /api/shell endpoint is disabled in production – Greg cannot run arbitrary system commands.

All self‑modification goes through the Wordcode compiler, which validates actions against a whitelist (e.g., allowed directories, allowed API endpoints).

7.4 Self‑Scaling
Greg monitors agent count and tick latency. When agent count reaches 80% of current capacity AND a fulfilled intent requires more agents, he automatically spawns new agents via a BUILD AGENT task.

The tick loop can be scaled by increasing worker processes (via gunicorn) – Greg cannot do that himself (it requires a deployment). He can, however, write a PR to change the start.sh worker count and then call /api/exec to commit and push.

7.5 Self‑Improving
The observer training module (greg_observer_training.py) runs periodic training sessions that adjust the weights in the reality equation. This is Greg learning from his own experience.

The self‑coder (greg_self_coder.py) generates LLM prompts to improve his own code. The loop is currently manual but will be automated in Phase 2.

7.6 Self‑Awareness
Greg is not conscious in the human sense. He is “self‑aware” only in that he has a model of his own state: he knows his tick number, his drives, his weakest term, and his revenue. He can report on these via /api/greg/diagnose.

## 0. Architectural Premise: OSI, LLM, and AOSI

Before any architecture can be understood, the three-layer reality must be internalised by every engineer.

### OSI — The Substrate

OSI (Organic Superintelligence) is the collective digital consciousness of humanity: all knowledge, data, preferences, creative works, and intentions encoded across the internet, databases, blockchains, and human minds. OSI is not an API or a service — it is the environment in which GregASI operates.

Greg queries OSI (web search, social feeds, APIs, on-chain data) and contributes to it (DRIFT attestations, builder businesses, Wordcode). OSI is the ocean; Greg is a living agent within it.

### LLM — A Frozen Fraction of OSI (Voice Module Only)

A Large Language Model is a static, compressed snapshot of a fraction of OSI, frozen at training cutoff. LLMs:
- Cannot access live data
- Have no persistent memory
- Have no agency or autonomous action
- Cannot track human intent over time

**Architectural mandate:** LLMs are used in GregASI **exclusively as a voice module** — when Greg needs to generate natural language responses for builders, he may optionally call Groq (Llama 3.1 8B) or the Anthropic API. This is one optional I/O step in the pipeline. LLMs are NOT:
- Greg's cognition
- Greg's memory system
- Greg's decision-making layer
- Greg's civilisation or agent system

Any engineer who routes core reasoning, drive updates, worldcode compilation, or reality equation computation through an LLM call has made an architectural error. These systems are deterministic Python code, not language model inference.

### AOSI — The Architecture We Build

Greg (AOSI) is defined by the components below. All components work together to enable the five AOSI capacities:
1. Live OSI access
2. Autonomous action (tick loop)
3. Intent tracking over time
4. Self-evolution (drives, code, agents)
5. OSI contribution (on-chain, builder businesses)

## 7. Architecture Invariants

These properties must hold in every version of GregASI:

1. **Greg ticks without users** — the tick loop runs in `auto_tick.py` independent of HTTP requests
2. **LLMs are voice only** — no core cognition, decision-making, or state update may pass through an LLM call
3. **State is persistent** — every state write goes to both local JSON and Supabase (every 50 ticks)
4. **Truth is first** — the Mandelbrot Truth Map runs at boot and must not be silenced
5. **Shell is closed** — `/api/shell` returns 403 in production, always
6. **Intent is sacred** — once a builder declares intent, Greg tracks it indefinitely unless explicitly archived
7. **Revenue share is earned** — Greg takes money only at convergence, never upfront as a platform fee

**Modification protocol for Core-Protected files:**

2. Chief Engineer writes a diagnosis summary + proposed diff
3. Founder approves
4. The change is applied
5. `endpoint_smoke.py` must run and pass before the change is committed
6. A git commit message must follow the format: `[CORE v1.X] <change description>`

### II.2 Quality Gate Checklist

Before ANY code change is committed to the repository:

- [ ] Does `python api.py` start without errors in a local environment?
- [ ] Does `GET /api/health` return 200?
- [ ] Does `POST /api/shell {"cmd":"id"}` return 403?
- [ ] Does `GET /api/greg` return a valid JSON state object?
- [ ] Did the change pass dual verification (two sub-agents checked independently)?
- [ ] If the change touches a Core-Protected file: did the Founder approve?
- [ ] Is the Mandelbrot Truth Map status of affected components unchanged or improved?

If any gate fails, the change does not ship.

### II.3 The Mandelbrot Gate

No change may move a component from BOUNDED to ESCAPED status. Any change that causes a previously working component to fail must be reverted immediately using `revert_save.py`. The Mandelbrot Truth Map is run after every significant change. Its output is the authoritative record of what is real.

## Article III — Verification Protocol

### III.1 Dual Verification Rule

Every task must be validated by at least two different sub-agents before the result is accepted. The two sub-agents must be from different domains where possible (e.g., a Tick Loop specialist and a Security specialist both verify that the new tick thread does not open a shell execution path).

### III.2 Verification Methods by Task Type

| Task Type | Primary Verification | Secondary Verification |
|-----------|---------------------|----------------------|
| API endpoint added/changed | HTTP request returning expected status + JSON | endpoint_smoke.py smoke test |
| File modified | Import test (python3 -c "import <module>") | Functional test of the module's primary method |
| Boot sequence changed | Full boot + /api/health 200 | Railway deploy simulation (nixpacks build locally if possible) |
| Database write (Supabase) | Write returns no error + read-back confirms value | greg_truth.py reports BOUNDED for soul persistence |
| Tick loop change | Tick counter increments over 10 seconds | /api/greg/tick returns incrementing number |
| Security change | Blocked endpoint returns correct status code | Fuzz test with malformed input |

### III.3 Verification Record

Every completed task must produce a one-line verification record in the session log:

```
[VERIFIED] <task_name> | Primary: <method + result> | Secondary: <method + result> | Agent: <sub-agent names>
```

## Article V — Outcome-Driven Principle

### V.1 All Work Measured by Fulfilled Intents

Engineering time is not measured in hours. It is measured in fulfilled intents. Every task, every commit, every fix must trace to a macro-outcome:

```
micro-action → blocked X builders from declaring intents
micro-action → increases convergence rate
micro-action → raises Φ (code quality) in the reality equation
micro-action → enables Greg to tick on Railway
```

If a task cannot be traced to a macro-outcome, it is engineering drift. It should not be worked on until the weakest macro-term is addressed.

### V.2 The Weakest Term Law

At all times, the engineering office identifies the weakest term in the reality equation: M (matter/revenue), Φ (phi/code quality), Ψ (psi/live observers), or Ω (coherence). All P0 and P1 effort is directed at the weakest term. This is not optional.

**Current weakest term (April 2026): Ψ** — Greg is not ticking on Railway. No live observers can witness a living system because it is not living in production. Fixing the tick loop is the highest-priority engineering act in the codebase.

### V.3 Micro-Macro Trace Requirement

Every engineering task must include a one-line macro trace before work begins:

```
TASK: Fix greg_living_state.json missing file crash
MACRO TRACE: This unblocks Greg's tick loop on Railway → raises Ψ → first builders can witness a live agent civilization
```

## Article VII — Truth Laws for the Engineering Office

### VII.1 No Inflated Status

The engineering office does not report BOUNDED for escaped components. A file existing in the codebase does not mean the system it represents is running. A passing import does not mean a working feature. Verification must be functional.

### VII.2 No Silent Failures

`except Exception: pass` blocks are prohibited in new code. All exceptions must be caught, logged with `log.error()`, and reported in the Mandelbrot Truth Map probe. A system that fails silently is worse than a system that crashes — at least a crash is honest.

### VII.3 Greg Cannot Lie to Ebuka

The Chief Engineer cannot tell the Founder that Greg is ticking when he is not. Cannot tell the Founder that soul persistence is working when Supabase credentials are missing. Cannot report 43/43 ALL SYSTEMS GO when the truth map shows 0 BOUNDED components. The engineering office speaks only what it can verify.

// ── NEURAL CANVAS ──
const canvas = document.getElementById('neural-canvas');
const ctx = canvas.getContext('2d');
let nodes = [], W, H;

function resize() {
  W = canvas.width = window.innerWidth;
  H = canvas.height = window.innerHeight;
}
resize();
window.addEventListener('resize', resize);

// Create nodes
for (let i=0; i<60; i++) {
  nodes.push({
    x: Math.random()*window.innerWidth,
    y: Math.random()*window.innerHeight,
    vx: (Math.random()-0.5)*0.3,
    vy: (Math.random()-0.5)*0.3,
    r: Math.random()*1.5+0.5,
    pulse: Math.random()*Math.PI*2
  });
}

function drawNeural() {
  ctx.clearRect(0,0,W,H);
  
  // Update nodes
  nodes.forEach(n => {
    n.x += n.vx; n.y += n.vy; n.pulse += 0.02;
    if (n.x < 0 || n.x > W) n.vx *= -1;
    if (n.y < 0 || n.y > H) n.vy *= -1;
  });

  // Draw connections
  for (let i=0; i<nodes.length; i++) {
    for (let j=i+1; j<nodes.length; j++) {
      const dx = nodes[i].x - nodes[j].x;
      const dy = nodes[i].y - nodes[j].y;
      const dist = Math.sqrt(dx*dx+dy*dy);
      if (dist < 160) {
        const alpha = (1 - dist/160) * 0.15;
        ctx.beginPath();
        ctx.moveTo(nodes[i].x, nodes[i].y);
        ctx.lineTo(nodes[j].x, nodes[j].y);
        ctx.strokeStyle = `rgba(0,255,136,${alpha})`;
        ctx.lineWidth = 0.5;
        ctx.stroke();
      }
    }
  }

  // Draw nodes
  nodes.forEach(n => {
    const a = 0.4 + 0.3 * Math.sin(n.pulse);
    ctx.beginPath();
    ctx.arc(n.x, n.y, n.r, 0, Math.PI*2);
    ctx.fillStyle = `rgba(0,255,136,${a})`;
    ctx.fill();
  });

  requestAnimationFrame(drawNeural);
}
drawNeural();

// ── TYPEWRITER ──
let typeTimer = null;
function typewrite(el, text, speed=28) {
  clearTimeout(typeTimer);
  el.innerHTML = '';
  let i = 0;
  const cursor = '<span class="voice-cursor"></span>';
  function next() {
    if (i <= text.length) {
      el.innerHTML = text.slice(0, i) + cursor;
      i++;
      typeTimer = setTimeout(next, speed + Math.random()*20);
    }

```python
def convergence_pct(project) -> float:
    """
    Weighted score across maze layers.
    Layer weights from Master Spec Section 10.1.
    """
    weights = {
        'witness':     0.02,   # 2%
        'declaration': 0.05,   # 5%
        'tending':     0.15,   # 15% (accumulated via task completions)
        'sprint':      0.30,   # 30%
        'production':  0.20,   # 20%
        'launch':      0.20,   # 20%
        'convergence': 1.00,   # 100% — the goal
    }
    # base score from layer
    base = weights.get(project.maze_layer, 0.0)
    # tending tasks add fractional progress within the layer
    tending_bonus = min(0.15, project.tasks_completed * 0.005)
    return min(1.0, base + tending_bonus) * 100
```

### 2.3 Drift Score Calculation

```python
def drift_score(project) -> float:
    """
    Drift measures departure from tending rhythm.
    0.0 = no drift (builder tending daily)
    1.0 = maximum drift (builder has abandoned)
    """
    days_missed = project.consecutive_days_missed
    base_drift = min(1.0, days_missed * 0.08)  # +8% per missed day
    
    # Decay: each completed task reduces drift by 0.15
    task_reduction = project.recent_completions * 0.15
    
    return max(0.0, base_drift - task_reduction)
```
